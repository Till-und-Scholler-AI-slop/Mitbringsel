# Live-Sync, Offline und Konfliktauflösung

Der Sync entsteht in zwei Phasen: Phase 5 verteilt Änderungen live per WebSocket, Phase 6 macht Artikel offline-fähig. Der Abschnitt [Stand Phase 5](#stand-phase-5) beschreibt, was zuerst gebaut wird. Was erst mit Phase 6 kommt, ist unten ausdrücklich so markiert.

## Stand Phase 5

Entscheidung und Alternativen: [ADR 0005](adr/0005-live-sync-phase-5.md).

- **REST schreibt, der WebSocket verteilt.** Alle Änderungen laufen wie bisher über REST. Der Server vergibt die HLC (`item.Clock`) und `serverSeq` und sendet das Ergebnis nach dem Commit als Ereignis an die Mitglieder der Gruppe. Outbox und HLC vom Client kommen mit Phase 6.
- **Kein `subscribe`:** Beim Verbinden trägt der Server die Verbindung in alle Gruppen des Nutzers ein und sendet `ready`. Nach jedem `ready` lädt der Client per REST neu: Gruppen, Listen und Artikel aller Haushalte (siehe Vorladen unten). So gleicht sich eine Verbindung nach einer Unterbrechung ohne `sync` wieder an.
- **Best Effort:** Ein langsamer oder getrennter Client verpasst Ereignisse. Die Datenbank ist die Wahrheit, REST holt alles nach.
- **Reihenfolge über `serverSeq`:** Ereignisse können vertauscht ankommen. Der Client wendet Artikel- und Listen-Ereignisse nur an, wenn die `serverSeq` größer ist als die gespeicherte.
- **Ereignisse tragen den Stand:** `itemChanged` und `listChanged` enthalten das ganze Objekt. `groupChanged` ist nur ein Hinweis, `GET /groups` neu zu laden, weil `Group` die Rolle des jeweiligen Nutzers enthält. Jedes Ereignis nennt die `actorId`, damit die UI „gerade geändert“ von anderen erkennt.
- **Löschen:** Listen werden hart gelöscht (`listDeleted`), Artikel als Tombstone (`itemDeleted`, bei „Abgehakte entfernen“ gesammelt als `itemsDeleted`).
- **Typen:** Alle Nachrichten stehen als Schemas in `api/openapi.yaml` (`ClientMessage`, `ServerMessage`); Go- und TypeScript-Typen werden daraus erzeugt.

## Zielbild ab Phase 6

Entscheidung und Alternativen: [ADR 0006](adr/0006-offline-phase-6.md).

Jede Änderung an einem Artikel wird zuerst lokal angewendet, in einer Warteschlange (Outbox) in IndexedDB gespeichert und dann als REST-Aufruf an den Server geschickt. Der Server entscheidet per Last Write Wins und verteilt das Ergebnis per WebSocket an alle verbundenen Gruppenmitglieder. Der WebSocket bleibt eine Einbahnstraße vom Server zu den Clients.

```
Client A (Vue)                 Go-Server                         Client B (Vue)
┌───────────────────┐          ┌────────────────────┐            ┌───────────────────┐
│ Store + IndexedDB │          │ item.Service (LWW) │            │ Store + IndexedDB │
│        │          │──REST───▶│         │          │            │        ▲          │
│ Outbox            │◀─Antwort─│ WebSocket-Hub      │──Ereignis─▶│ WebSocket         │
└───────────────────┘          └─────────┬──────────┘            └───────────────────┘
                                         │ LWW + serverSeq
                                         ▼
                                    PostgreSQL
```

Die Antwort auf den REST-Aufruf trägt den gespeicherten Artikel; die Änderung verlässt die Outbox. Alle Verbindungen der Gruppe erhalten das Ereignis (`itemChanged`). Offline bleiben Änderungen in der Outbox, bis die Verbindung zurück ist.

## Grundprinzipien

- **Offline-first für Artikel:** Die UI liest immer aus dem lokalen Zustand (Pinia, gespiegelt in IndexedDB). Das Netzwerk ist nur der Transport.
- **IDs vom Client:** Neue Artikel bekommen eine UUIDv7 auf dem Client. So kann man offline Artikel anlegen und später ohne ID-Konflikte synchronisieren.
- **Optimistische Updates:** Die Änderung ist sofort in der UI sichtbar. Lehnt der Server sie ab, wird sie zurückgerollt und der Nutzer bekommt einen Hinweis.
- **Wiederholen ist harmlos:** Geht eine Antwort verloren, sendet die Outbox dieselbe Änderung noch einmal. Ein zweites Anlegen mit derselben ID in derselben Liste gibt den gespeicherten Artikel zurück, eine Änderung mit derselben HLC gewinnt nicht gegen die gespeicherte, ein zweites Löschen trifft nur den Tombstone. Eine eigene `opId` braucht es deshalb nicht.

## Konfliktauflösung: Last Write Wins pro Feld

Status: entschieden (siehe [ADR 0004](adr/0004-lww-pro-feld.md)).

- **Regel:** LWW pro Feld statt pro Artikel. Hakt Person A einen Artikel ab, während Person B die Menge ändert, bleiben beide Änderungen erhalten. Nur wenn beide dasselbe Feld ändern, gewinnt die spätere Änderung.
- **Zeitstempel:** Jede Änderung trägt einen Zeitstempel einer Hybrid Logical Clock (HLC). Ab Phase 6 kommt er vom Client (Feld `clock` bei `createItem` und `updateItem`); fehlt er, stempelt der Server selbst. Der Client übernimmt die Uhren jedes Artikels, den er empfängt, damit seine nächste Änderung neuer ist als alles, was er gesehen hat. Die HLC kombiniert Uhrzeit und Zähler und bleibt auch bei leicht abweichenden Geräteuhren konsistent. Zeitstempel, die mehr als 5 Minuten in der Zukunft liegen, setzt der Server auf seine eigene Zeit.
- **HLC-Format:** Eine HLC stempelt die Änderung eines einzelnen Feldes, sie identifiziert nicht den Artikel. Sie ist ein Text fester Breite, `<Zeit>-<Zähler>-<Knoten>`, z.B. `0000019a2b3c4d5e-0001-3f2a9c`: Millisekunden seit 1970 (16 Hex-Ziffern, klein), Zähler (4 Hex-Ziffern, klein) und Knoten-ID (1 bis 64 Zeichen aus `A-Z a-z 0-9 _ -`). Im Frontend würfelt jeder Tab beim Laden eine eigene, zufällige Knoten-ID; der Server nutzt `srv-…` für Änderungen ohne Uhr. Wegen der festen Breite ist der Textvergleich (`<`, `>`) schon der HLC-Vergleich, in Go wie in TypeScript. Umsetzung: `backend/internal/item/hlc.go` und `frontend/src/services/sync/hlc.ts`, mit gemeinsamen Testfällen in `api/testdata/hlc.json`.
- **Felder mit Uhr:** `name`, `quantity`, `unit`, `note` und `checked`. `checked_by` und `checked_at` gehören zur Uhr von `checked`. Die Uhren stehen in `items.field_clocks`, `Merge` (`backend/internal/item/merge.go`) entscheidet, welche Felder einer Änderung gewinnen.
- **Gleiche Änderung zweimal:** Eine gleiche HLC gewinnt nicht gegen die gespeicherte; eine erneut gesendete Änderung ändert also nichts.
- **Archivierte Listen:** Artikel in einer archivierten Liste bleiben änderbar, damit Offline-Änderungen aus der Zeit vor dem Archivieren nicht verloren gehen.
- **Löschen gewinnt:** Gelöschte Artikel werden als Tombstone (`deleted_at`) markiert und nicht wiederbelebt, auch wenn später eine Offline-Bearbeitung eintrifft. Tombstones werden nach 30 Tagen endgültig entfernt.
- **Gleichstand:** Bei identischem Zeitstempel entscheidet der lexikografische Vergleich der Client-IDs, damit alle Geräte zum selben Ergebnis kommen.

## Synchronisationsablauf (ab Phase 6)

1. Nutzer ändert einen Artikel. Der Client stempelt die Änderung mit seiner HLC, zeigt sie sofort an, speichert sie in IndexedDB und legt sie in die Outbox.
2. Die Outbox sendet ihre Änderungen der Reihe nach als REST-Aufrufe, immer eine zur Zeit. Nur ein Tab sendet (`navigator.locks`).
3. Der Server prüft Session und Gruppenmitgliedschaft, wendet LWW in einer Transaktion an und vergibt eine neue `serverSeq`.
4. Die Antwort trägt den gespeicherten Artikel. Der Client übernimmt ihn, die Änderung verlässt die Outbox. Alle Verbindungen der Gruppe bekommen das Ereignis (`itemChanged`); die anderen Clients übernehmen es, wenn dessen `serverSeq` größer ist als die gespeicherte.
5. Netzfehler, 5xx, 408 und 429 wiederholt die Outbox mit Backoff. Bei 401 hält sie an und behält alles. Jedes andere 4xx (etwa 400, 403, 404, 409) verwirft die Änderung, der Artikel zeigt wieder den Stand des Servers, und ein Toast nennt den Grund.

## Wiederverbinden nach Offline-Phase (ab Phase 6)

1. Der Client baut den WebSocket neu auf (exponentielles Backoff, maximal 30 Sekunden).
2. Nach `ready` stößt der Client die Outbox an (sie sendet auch ohne Socket, sobald der Browser online ist) und lädt Gruppen, Listen und Artikel vollständig neu, die Artikel mit einer Anfrage pro Haushalt (`GET /groups/{groupId}/items`). Die Antwort nennt außerdem in `listIds` die aktiven Listen, die sie vollständig abdeckt, auch leere; so unterscheidet der Client „leer“ von „nicht abgedeckt“. Senden und Laden dürfen gleichzeitig laufen: Felder mit ausstehenden Änderungen liegen über dem geladenen Stand, bis die Antwort des Servers kommt.

Einen Abgleich ab einer `serverSeq` (Delta) gibt es bewusst nicht: `serverSeq` folgt nicht der Reihenfolge der Commits, ein Delta könnte Änderungen dauerhaft übersehen (siehe [ADR 0006](adr/0006-offline-phase-6.md)).

## WebSocket-Protokoll

Alle Nachrichten sind JSON mit einheitlichem Umschlag: `{ "type": "...", "payload": { ... } }`. Es gibt kein `id`-Feld; `ping`, `pong` und `ready` haben keine `payload`. Die Formen stehen in `api/openapi.yaml` (`ClientMessage` und `ServerMessage`, jeweils mit `type` als Unterscheidungsmerkmal).

| Richtung | Typ | Inhalt | Ab |
| --- | --- | --- | --- |
| Client → Server | `ping` | Verbindung am Leben halten (alle 25 Sekunden) | Phase 5 |
| Server → Client | `ready` | Verbindung steht, alle Gruppen des Nutzers sind eingetragen; der Client lädt per REST neu | Phase 5 |
| Server → Client | `pong` | Antwort auf `ping` | Phase 5 |
| Server → Client | `itemChanged` | Artikel angelegt oder geändert: `groupId`, `actorId`, ganzer Artikel mit `serverSeq` | Phase 5 |
| Server → Client | `itemDeleted` | Artikel gelöscht: `groupId`, `listId`, `itemId`, `serverSeq`, `actorId` | Phase 5 |
| Server → Client | `itemsDeleted` | Mehrere Artikel gelöscht („Abgehakte entfernen“): `groupId`, `listId`, `actorId`, je Artikel `itemId` und `serverSeq` | Phase 5 |
| Server → Client | `listChanged` | Liste angelegt, umbenannt, archiviert oder wieder aktiviert: `actorId`, ganze Liste mit `serverSeq` | Phase 5 |
| Server → Client | `listDeleted` | Liste gelöscht: `groupId`, `listId`, `actorId` | Phase 5 |
| Server → Client | `groupChanged` | Name, Mitglieder oder Rollen geändert; Hinweis, `GET /groups` neu zu laden | Phase 5 |
| Server → Client | `groupRemoved` | Gruppe gelöscht oder Nutzer entfernt (`reason`: `deleted`, `removed`) | Phase 5 |
| Server → Client | `error` | Fehlercode (`ErrorCode`) | Phase 5 |

Auch mit Phase 6 kommen keine neuen Nachrichten dazu: Der Client schreibt per REST (siehe [ADR 0006](adr/0006-offline-phase-6.md)).

### Ping und Pong

Browser können keine WebSocket-Protokoll-Pings senden. Der Client schickt deshalb alle 25 Sekunden eine `ping`-Nachricht, der Server antwortet mit `pong` und trennt eine Verbindung nach 60 Sekunden Stille. Das hält auch Traefik offen.

### Reihenfolge und Zustellung

- Der Server sendet nach dem Commit, aber ohne globale Ordnung. Zwei Ereignisse zum selben Artikel können vertauscht ankommen; der Client wendet ein Ereignis nur an, wenn dessen `serverSeq` größer ist als die gespeicherte.
- Auch die Verbindungen des Absenders bekommen das Ereignis (Broadcast an den ganzen Raum). Die REST-Antwort trägt dieselbe `serverSeq`; der Tab, der die Änderung gemacht hat, verwirft das Ereignis, weil dessen `serverSeq` nicht größer ist als die gespeicherte.
- Zwei gleichzeitige Löschvorgänge können beide einen lebenden Artikel sehen und `itemDeleted` zweimal mit derselben `serverSeq` senden. Der zweite wird aus demselben Grund verworfen.
- Die Zustellung ist Best Effort. Wer ein Ereignis verpasst (Verbindung weg, zu langsam), holt es mit dem Neuladen nach dem nächsten `ready` nach.
- Mitgliedschaften bestimmen, wer Ereignisse bekommt: Wer in eine Gruppe aufgenommen wird, wechselt mit seinen Verbindungen in deren Raum; wer sie verlässt, bekommt `groupRemoved` und verlässt den Raum.
- Die Reihenfolge beim Hub ist je Fall festgelegt, und die Raumwechsel laufen immer, auch wenn eine Nachricht nicht kodiert werden kann:
  - **Aufnehmen** (Gruppe anlegen, Einladung annehmen): erst `JoinGroup`, dann `groupChanged` an den Raum. Die neuen Verbindungen bekommen den Hinweis also selbst und laden die Gruppen neu.
  - **Entfernen:** erst `LeaveGroup`, dann `groupRemoved` (`removed`) an alle Verbindungen des Entfernten (`SendToUser`, auch an solche, die noch laden), dann `groupChanged` an die übrigen Mitglieder. Der Entfernte bekommt `groupChanged` nicht; die `actorId` von `groupChanged` ist der Entfernende (beim Austreten der Austretende selbst).
  - **Löschen:** erst `groupRemoved` (`deleted`) an den Raum, dann `RemoveGroup`. Andersherum würde niemand benachrichtigt.
- Der Client verwirft Ereignisse zu Gruppen oder Listen, die er nicht kennt (nach `groupRemoved` oder `listDeleted`, oder bevor er sie geladen hat), statt sie anzulegen. `groupRemoved` kann auch vor `ready` eintreffen, weil es auch Verbindungen erreicht, die noch laden; der Client behandelt es wie sonst.
- Zwei Rennen nehmen wir bewusst hin, weil die Datenbank stimmt und das nächste `ready` es korrigiert: Wird eine Einladung fast gleichzeitig mit dem Löschen der Gruppe angenommen, kann die Verbindung in einen Raum geraten, den es nicht mehr gibt, und bleibt dort bis zum Trennen ohne Ereignisse. Wird jemand entfernt und im selben Moment wieder aufgenommen, kann `LeaveGroup` nach `JoinGroup` laufen, und er fehlt im Raum, bis er sich neu verbindet.

## Server-Seite

- **Hub:** Das Paket `backend/internal/realtime` verwaltet die Verbindungen als Räume pro Gruppe. Es kennt keine Domäne und verteilt nur Bytes. Jede Verbindung hat einen gepufferten Sendekanal; langsame Clients werden getrennt statt den Hub zu blockieren. Beim Verbinden wird die Verbindung erst registriert und dann werden die Gruppen geladen; Entfernen aus einer Gruppe oder Löschen einer Gruppe während des Ladens merkt sich der Hub, damit die Verbindung nicht in einen Raum gerät, den sie nicht mehr betreten darf. Pro Nutzer gilt ein Limit: Die 11. Verbindung wird abgewiesen, die älteste bleibt bestehen. Der Name `sync` entfällt, weil er mit der Standardbibliothek kollidiert; die Konfliktauflösung bleibt im Paket `item`.
- **Veröffentlichen:** Die Services `item`, `list` und `group` rufen nach dem Commit und nur bei echten Änderungen ein kleines `Publisher`-Interface auf. In `httpapi` setzt ein `Broadcaster` daraus die Nachrichten zusammen. Der Publisher blockiert nie und gibt keinen Fehler zurück, denn die Änderung ist gespeichert, egal ob jemand sie erfährt. Beim Artikel-Service (`item.Publisher`) gilt:
  - **Anlegen:** `itemChanged` nach dem Speichern, nicht bei einer Wiederholung derselben Anfrage (gleiche ID in derselben Liste).
  - **Ändern:** `itemChanged` erst nach dem Commit der Transaktion und nur, wenn mindestens ein Feld gewonnen hat. Verliert jedes Feld den Merge oder ist der Artikel ein Tombstone, ändert sich nichts und es gibt weder Ereignis noch neue `serverSeq`.
  - **Löschen:** `itemDeleted` nur beim ersten Löschen. Löschen eines Tombstones ändert nichts.
  - **Abgehakte entfernen** (`POST /lists/{listId}/items/remove-checked`): Der Client schickt die IDs, die er als abgehakt zeigt (höchstens 500). Der Server löscht davon in einer Anweisung die, die zur Liste gehören, noch abgehakt und nicht gelöscht sind; jeder Artikel bekommt einen Tombstone und eine eigene `serverSeq`. Ein inzwischen wieder aufgehakter Artikel bleibt, ebenso einer, den jemand erst danach abgehakt hat. Die Zeilen werden in ID-Reihenfolge gesperrt, damit zwei gleichzeitige Anfragen sich nicht gegenseitig blockieren. Die Antwort nennt die gelöschten Artikel mit `serverSeq`; die Gruppe bekommt ein `itemsDeleted`, keins, wenn nichts gelöscht wurde.

  Beim Listen-Service (`list.Publisher`) gilt:
  - **Anlegen, Umbenennen, Archivieren, Reaktivieren:** `listChanged` mit der gespeicherten Liste (samt `serverSeq`), nach dem Schreiben. Eine Änderung, die nichts ändert, wird übersprungen: derselbe Name, Archivieren einer archivierten oder Reaktivieren einer aktiven Liste schreiben nichts, vergeben keine neue `serverSeq` und senden kein Ereignis. Der Service liest die Liste dafür vor dem Schreiben; die Anfrage gilt als zum Zeitpunkt dieses Lesens ausgeführt.
  - **Löschen:** `listDeleted` nach dem Löschen, mit der Gruppe der Liste, die der Service vorher gelesen hat. Zwei gleichzeitige Löschvorgänge: der zweite findet keine Zeile (`ErrNotFound`) und sendet nichts. Die Artikel der Liste bekommen kein eigenes Ereignis; der Client verwirft sie mit der Liste.

  Beim Gruppen-Service (`group.Publisher`) gilt:
  - **Anlegen:** Die Gruppe hat kein eigenes Ereignis, sie entsteht über `MemberJoined`: Die Verbindungen des Erstellers treten dem Raum bei, danach geht `groupChanged` an den Raum. Das passiert nach dem Commit und vor dem Laden der Antwort; scheitert das Laden, existiert die Gruppe trotzdem und der Ersteller ist im Raum.
  - **Umbenennen:** `groupChanged` nur, wenn sich der Name ändert. Derselbe Name schreibt nichts. Die Rechteprüfung kommt vor diesem Vergleich, ein Außenstehender bekommt also denselben Fehler wie bisher.
  - **Rolle ändern:** `groupChanged` nur, wenn sich die Rolle ändert. Dieselbe Rolle ändert nichts (der Service erkennt das in der Transaktion).
  - **Einladung annehmen:** `MemberJoined` nur, wenn wirklich jemand aufgenommen wurde (`AddMemberIfAbsent` meldet das). Wer schon Mitglied ist oder den Link ein zweites Mal öffnet, löst nichts aus.
  - **Mitglied entfernen oder Austreten:** `MemberRemoved` nach dem Commit. Der Owner kann nicht austreten (`ErrOwnerImmutable`), dabei gibt es kein Ereignis.
  - **Gruppe löschen:** `GroupDeleted` nach dem Löschen. Listen und Artikel bekommen kein eigenes Ereignis; der Client verwirft sie mit der Gruppe.
- **Authentifizierung:** `GET /api/v1/ws` liegt hinter der Session-Prüfung. Die `Origin` muss zum Host von `PUBLIC_BASE_URL` passen, sonst `403 CROSS_ORIGIN_REQUEST`. Der Schutz gegen Cross-Origin-Anfragen aus der Standardbibliothek greift hier nicht, weil er GET durchlässt und der Vite-Proxy im Dev-Betrieb den `Host`-Header umschreibt.
- **Lebensdauer und Limits:** Eine Verbindung lebt höchstens etwa eine Stunde, damit die Session beim Wiederverbinden neu geprüft wird. Pro Nutzer sind etwa 10 Verbindungen erlaubt. Beim Logout schließt das Frontend den Socket, beim Herunterfahren schließt der Server alle Verbindungen selbst und wartet innerhalb des Shutdown-Timeouts, bis die aktiven WebSocket-Handler ihre Close-Frames geschrieben haben.
- **Fristen und Größen:** Der Server liest höchstens 4 KiB pro Nachricht (der Client sendet nur `ping`). Er trennt eine Verbindung nach 60 Sekunden ohne Nachricht und gibt jeder Nachricht beim Schreiben 10 Sekunden. Die Verbindung wird ohne Kompression geführt.
- **Unbekannter Typ:** Eine Nachricht mit einem Typ, den der Server nicht kennt, beantwortet er mit `error` (`INVALID_REQUEST`) und lässt die Verbindung offen, damit ein Client einer anderen Version nicht getrennt wird. Neue Nachrichtentypen kommen als Eintrag in die Handler-Registry (`newWSHandlers` in `httpapi/ws.go`).
- **Schließcodes:** Der Server schließt, wenn er einen Grund hat, mit einem Close-Frame. Das Frontend verbindet sich in allen Fällen neu (mit Backoff) und lädt nach `ready` per REST nach; der Code sagt nur, warum.

  | Code | Grund (Text im Frame) | Anlass |
  | --- | --- | --- |
  | 1001 | `server shutting down` | Server wird heruntergefahren (`Hub.Close`) |
  | 1001 | `connection lifetime reached` | Verbindung ist eine Stunde alt |
  | 1003 | `text messages only` | Binärnachricht |
  | 1008 | `invalid message` | Kein JSON, kein Umschlag `{type, payload}` oder `type` leer |
  | 1009 | (von der Bibliothek) | Nachricht größer als 4 KiB |
  | 1011 | `internal error` | Gruppen konnten nicht geladen werden oder ein Handler ist gescheitert |
  | 1013 | `too slow` | Sendepuffer voll, siehe Hub |
  | 1006 (kein Frame) | | 60 Sekunden Stille, Schreib-Timeout oder Netzabbruch: Der Browser meldet 1006, weil kein Close-Frame ankommt |
- **Eine Instanz:** Für den Start läuft ein einzelner Backend-Container. Muss später horizontal skaliert werden, verteilt PostgreSQL `LISTEN/NOTIFY` die Änderungen zwischen Instanzen. Das wird erst bei Bedarf gebaut.

## Client-Seite

Der Code liegt in `frontend/src/services/sync/socket.ts` (Verbindung) und `frontend/src/stores/sync.ts` (Anbindung an den angemeldeten Nutzer).

- **Lebensdauer:** Der Sync-Store öffnet die Verbindung, sobald ein Nutzer angemeldet ist, und schließt sie bei Logout, abgelaufener Session oder Nutzerwechsel (Close-Code 1000, kein Wiederverbinden). Der Store hat keine Aktionen; `main.ts` erzeugt ihn nur.
- **URL:** `ws://` oder `wss://` (je nach Schema der Seite), Host der Seite, Pfad `/api/v1/ws`. In Entwicklung leitet der Vite-Proxy den Upgrade weiter.
- **Status:** `idle` (gestoppt, kein Nutzer), `connecting` (erster Verbindungsaufbau und der erste neue Versuch nach einer verlorenen, funktionierenden Verbindung, damit das stündliche 1001 nicht kurz „offline“ anzeigt), `connected` (ab `ready`), `offline` (der Browser meldet offline oder seit dem letzten `ready` ist mindestens ein Versuch gescheitert). Eine Verbindung, die `ready` gemeldet hat, gilt als `connected`, auch wenn `navigator.onLine` `false` sagt; ist sie tot, merkt es der Ping.
- **Backoff:** Wartezeit vor Versuch *n* (ab 0) = `min(30 s, 1 s · 2^n) · (1 − 0,5 · Zufall)`, also ohne Jitter 1, 2, 4, 8, 16, 30, 30 s. Jeder Versuch zählt hoch, `ready` setzt auf 0 zurück. Nach einer verlorenen, funktionierenden Verbindung beginnt es also wieder bei etwa 0,5 bis 1 s.
- **Fristen:** Alle 25 Sekunden ab `open` sendet der Client `ping`. Nach einem `ping` läuft eine Frist von 10 Sekunden; jede eingehende Nachricht (nicht nur `pong`) beendet sie. Läuft sie ab, gibt der Client die Verbindung auf und baut sie neu auf, ohne auf das Close-Ereignis des Browsers zu warten (das kommt bei totem TCP sehr spät). Ebenso gilt ein Versuch als gescheitert, wenn 10 Sekunden nach dem Öffnen kein `ready` da ist.
- **Browser-Ereignisse:** `offline` bricht das Warten auf den nächsten Versuch ab; solange der Browser offline ist, gibt es keine neuen Versuche, eine offene Verbindung bleibt (der Ping erkennt, ob sie tot ist). `online` verbindet sofort, falls keine Verbindung besteht (der Backoff-Zähler bleibt). Ein versteckter Tab hält die Verbindung offen; wird er sichtbar, verbindet er sofort (keine Verbindung) oder sendet sofort einen `ping` (Verbindung steht).
- **Schließcodes:** Alle Codes führen zum Wiederverbinden mit Backoff, siehe [Server-Seite](#server-seite). Nur 1001 (Herunterfahren, Lebensdauer) und 1006 (Netz weg, 60 Sekunden Stille) laufen ohne Log; jeder andere Code (z.B. 1003, 1008, 1009, 1011, 1013) schreibt eine Warnung mit Code und Grund in die Konsole. Ein `error`-Ereignis des Browsers wird ignoriert, weil immer ein Close folgt.
- **Session prüfen:** Ein fehlgeschlagener Handshake zeigt nur 1006, nie den HTTP-Status. Nach jedem dritten gescheiterten Versuch in Folge (3, 6, 9 …) ruft der Sync-Store deshalb `GET /me` auf. Antwortet es mit `401`, beendet der Handler für abgelaufene Sessions die Sitzung, der Nutzer ist weg und der Store stoppt den Socket. Andere Fehler (Netz weg) bleiben ohne Folgen.
- **Nachrichten:** Der Client liest nur Text mit JSON-Umschlag und bekanntem `type`. Kaputtes JSON schreibt eine Warnung und wird ignoriert, ein unbekannter Typ (neueres Backend) still. Die Verbindung bleibt in beiden Fällen offen. Die Payload wird nicht geprüft. `error` schreibt zusätzlich eine Warnung.
- **Handler-Registry:** `socket.on(typ, handler)` meldet einen Handler für einen Nachrichtentyp an und liefert die Abmeldefunktion. Der Handler bekommt die Nachricht mit dem passenden Typ (`ServerMessageOf<T>`). Handler bleiben über Wiederverbinden und `stop()`/`start()` hinweg angemeldet; ein werfender Handler wird geloggt und hält die anderen nicht auf. Stores bekommen die Schnittstelle `ServerEvents` als Factory-Parameter (Standardwert `liveSocket`), damit Tests sie ersetzen können. Nutzer sind der Artikel-Store (Schritt 7), der Listen-Store und der Gruppen-Store (Schritt 8). Auf `ready` hören sie nicht selbst; das Neuladen danach steuert das Vorladen (unten). Ein Store meldet seine Handler beim Auflösen (`$dispose`) wieder ab.
- **Artikel-Store** (`frontend/src/stores/items.ts`): Alle Stände vom Server (Ereignis, Antwort auf Anlegen, Ändern, Abhaken, Laden) laufen durch eine Stelle und folgen denselben Regeln.
  - **Outbox-Lebensdauer:** Der Store besitzt die Outbox des angemeldeten Nutzers ([#132](https://github.com/Till-und-Scholler-AI-slop/Mitbringsel/issues/132)). Er öffnet sie beim Anmelden, liest vorhandene Einträge ein und stößt `trigger()` an; bei Logout, Nutzerwechsel und `$dispose` schließt er sie wieder.
  - **UUIDv7 und HLC:** Neue Artikel bekommen lokal eine UUIDv7; `create`, `update` und `setChecked` stempeln jede Änderung mit `hlc.next()` der Tab-Uhr. Der Store übernimmt per `hlc.observe` alle Uhren aus Ladeantworten, Ereignissen (auch verworfenen), dem Gerätespeicher und Outbox-Einträgen anderer Tabs.
  - **Reihenfolge:** Ein Ereignis gilt nur mit größerer `serverSeq` als der gespeicherte Stand, bei Gleichstand wird es verworfen. Eine Antwort auf eine eigene Anfrage gilt auch bei Gleichstand, weil sie derselbe Stand sein kann (Ereignis vor Antwort). Neue Artikel werden nach `createdAt`, dann `id` einsortiert, wie der Server sortiert (`createdAt` als Zeitpunkt verglichen, nicht als Text, weil der Server nachgestellte Nullen weglässt).
  - **Unbekannte Listen:** Ereignisse für eine Liste, die der Store nicht geladen hat, werden verworfen; beim Laden kommt der aktuelle Stand ohnehin.
  - **Löschen gewinnt:** Gelöschte Artikel merkt sich der Store bis zum Nutzerwechsel (Tombstone). Jeder spätere Stand dieses Artikels wird verworfen, egal mit welcher `serverSeq` (der Server nimmt nach dem Löschen keine Änderung mehr an). Das gilt für `itemDeleted`, `itemsDeleted`, eigenes Löschen und Artikel, die eine Antwort vom Laden nicht mehr enthält.
  - **Ausstehende Änderungen:** Die Anzeige legt die ausstehenden Änderungen (`services/sync/pending.ts`) über den bestätigten Server-Stand (`byList`): `local` (Änderungen dieses Tabs auf dem Weg in die Outbox), `stored` (zuletzt gelesene Einträge der Outbox, auch aus anderen Tabs über `subscribe`/`BroadcastChannel`), abzüglich `settled` (in diesem Tab bereits beantwortete oder abgelehnte `seq`, falls ein älteres Lesen sie noch enthält). Alle anderen Felder aus Ereignissen und Ladeantworten werden sofort übernommen; die Antwort des Servers ersetzt den Artikel und entfernt den Eintrag aus dem Overlay. Lehnt der Server eine Änderung ab, fällt der Artikel auf den Server-Stand zurück; `ITEM_NOT_FOUND` und (beim Anlegen) `ITEM_ID_TAKEN` werden still verworfen und als Tombstone gemerkt (der Artikel bzw. die Liste existiert ohnehin nicht mehr), `LIST_NOT_FOUND` bei `removeChecked` wird ebenfalls still verworfen (der Listen-Store räumt über `forgetList` auf), jede andere Ablehnung (auch `OUTBOX_EXPIRED`, beim Anlegen ebenfalls mit Tombstone) meldet der Store über `onRejected` — `useItemRejections` in `App.vue` zeigt dafür einen Fehler-Toast mit Artikelname (bei `removeChecked` ohne Namen, einmal je Entfernen) und Grund.
  - **Laden:** Die Antwort wird eingemischt, nicht übernommen. Ein Artikel mit größerer `serverSeq` im Store bleibt. Artikel, die während des Ladens eintrafen (Ereignis oder Antwort), bleiben, auch wenn die Antwort sie nicht kennt; alle anderen, die die Antwort nicht mehr enthält, gelten als gelöscht. Die Reihenfolge der Ereignisse bestimmt eine logische Uhr (ein Zähler statt Zeitstempel). Die Antwort eines Ladens, der vor dem zuletzt übernommenen gestartet ist, wird verworfen.
  - **Haushalt laden (`loadGroup`):** Eine Anfrage (`GET /groups/{groupId}/items`) lädt die Artikel aller aktiven Listen des Haushalts. Jede Liste aus `listIds` wird wie beim Laden einer Liste eingemischt und bekommt den Status `ready`; eine abgedeckte Liste ohne Artikel ist leer, auch im Speicher. Listen, die die Antwort nicht nennt (archivierte), bleiben unberührt. Eine Liste, die `forgetList` nach dem Start der Anfrage verworfen hat, kommt nicht zurück. Scheitert die Anfrage, ändert sich nichts, auch kein Status `error`, denn kein Screen hat sie angefordert.
  - **Neuladen (`reloadLoaded`):** Der Store lädt jede Liste neu, die nicht `idle` ist, auch eine, die gerade lädt, außer den übergebenen. Eine schon geladene Liste behält dabei den Status `ready`, es gibt keinen Spinner, auch nicht beim erneuten Öffnen in der Listenansicht. Scheitert das Neuladen, bleiben die Artikel stehen und der Status wird `error`.
  - **Abgehakte entfernen:** `startRemovingChecked` legt die abgehakten Artikel (einschließlich noch wartender Haken und unbestätigter neuer Artikel, in Blöcken zu höchstens 500 IDs) sofort als gehaltene Einträge (`enqueueHeld`) in die Outbox ([#133](https://github.com/Till-und-Scholler-AI-slop/Mitbringsel/issues/133)). Das Pending-Overlay blendet sie aus, solange sie abgehakt sind — auch in anderen Tabs desselben Browsers (`subscribe`/`BroadcastChannel`); hakt jemand einen Artikel in der Zwischenzeit auf, steht er wieder bei den offenen. Eine Web-Lock hält die Einträge zurück, solange der „Rückgängig“-Toast läuft (`useRemoveItems`, Hover pausiert die Uhr): „Rückgängig“ (`undo()`) entfernt die Einträge ungesendet aus der Outbox und gibt erst dann die Sperre frei; jedes andere Ende des Toasts (abgelaufen, geschlossen, von einem neueren verdrängt) gibt sie per `commit()` frei. Wird der Tab vorher geschlossen, neu geladen oder stürzt ab, gibt der Browser die Sperre von selbst frei, sodass ein anderer Tab oder der nächste Start das Entfernen nachholt. Was der Server gelöscht hat, bekommt einen Tombstone, der Rest taucht wieder auf; Ablehnungen (außer `LIST_NOT_FOUND`, still) meldet der Store einmal je Entfernen über `onRejected`.
  - **Einen Artikel löschen:** `startRemovingItem` (aus dem Artikelformular) blendet den Artikel sofort aus und bietet über `useRemoveItems` zunächst den „Rückgängig“-Toast (5 s). Erst `commit()` legt das Löschen in die Outbox, wo der Artikel bis zur Bestätigung ausgeblendet bleibt; wird der Tab noch während des Toasts geschlossen, geht das Löschen verloren. Der Artikel bleibt ausgeblendet, egal was andere in der Zwischenzeit ändern (Löschen gewinnt). Antwortet der Server mit `ITEM_NOT_FOUND`, zählt das in der Outbox als gesendet.
  - **Bearbeiten:** Das Formular merkt sich die Felder beim Öffnen, legt beim Speichern nur die geänderten Felder in die Outbox und schließt sofort. Ändert ein anderes Mitglied in der Zwischenzeit ein anderes Feld, bleibt dessen Wert (LWW pro Feld). Änderungen anderer überschreiben das Getippte nicht; löscht jemand den Artikel, schließt das Formular mit einem Hinweis. Im Formular stehen nur noch lokale Eingabeprüfungen; Ablehnungen des Servers erscheinen als Toast.
- **Listen-Store** (`frontend/src/stores/lists.ts`): Dieselben Regeln wie beim Artikel-Store, ohne Abhaken.
  - **Reihenfolge:** `listChanged` gilt nur mit größerer `serverSeq`, eine Antwort auf eine eigene Anfrage (Anlegen, Umbenennen, Archivieren) auch bei Gleichstand. Kommt das eigene Ereignis vor der Antwort, steht die Liste trotzdem nur einmal da. Neue Listen werden nach `createdAt`, dann `id` einsortiert.
  - **Unbekannte Gruppen:** Ereignisse für eine Gruppe, die der Store nicht geladen hat, werden verworfen.
  - **Löschen gewinnt:** Gelöschte Listen merkt sich der Store bis zum Nutzerwechsel; ein späteres `listChanged` (es kann `listDeleted` überholen) legt sie nicht wieder an. Das gilt für `listDeleted`, eigenes Löschen und Listen, die eine Antwort vom Laden nicht mehr enthält (sie liefert auch archivierte Listen, eine fehlende ist also gelöscht).
  - **`groupRemoved`:** Der Store verwirft die Gruppe samt Listen, ohne sie sich als gelöscht zu merken: Wer wieder eingeladen wird, sieht die Listen wieder.
  - **Artikel:** Der Listen-Store kennt als einziger die Zuordnung von Listen zu Gruppen. Verschwindet eine Liste (gelöscht oder Gruppe verlassen), ruft er `forgetList` im Artikel-Store auf; der verwirft die Artikel und lädt die Liste nicht mehr neu. Die Funktion ist ein Factory-Parameter, damit Tests sie ersetzen können.
  - **Laden:** wie beim Artikel-Store: Die Antwort wird mit einer logischen Uhr eingemischt, ein Neuladen zeigt keinen Spinner. Verschwindet die offene Liste, wechselt die Listenansicht zum Haushalt und öffnet die nächste aktive Liste.
- **Gruppen-Store** (`frontend/src/stores/groups.ts`): Gruppen haben keine `serverSeq`, und `groupChanged` trägt keinen Stand. Der Store lädt deshalb `GET /groups` neu und mischt die Antwort mit einer logischen Uhr ein.
  - **`groupChanged`:** Der Store lädt neu, falls er nicht `idle` ist. Eine Gruppe, in die man gerade aufgenommen wurde, kommt so mit. Mehrere Ereignisse kurz hintereinander laden parallel; die Antwort eines Ladens, der vor dem zuletzt übernommenen gestartet ist, wird verworfen. Eine geladene Gruppe behält den Status `ready`, es gibt keinen Spinner.
  - **Entfernen:** `groupRemoved`, eigenes Löschen und eigenes Austreten verwerfen die Gruppe sofort. Eine Ladeantwort, die vorher gestartet ist, bringt sie nicht zurück; ein späteres Laden schon (wieder eingeladen).
  - **Grund des Verschwindens:** Der Store merkt sich Name und Grund (`departureOf`): `removed` oder `deleted` aus `groupRemoved` eines anderen Mitglieds, `self` für eigenes Löschen und Austreten (auch per `groupRemoved` mit der eigenen `actorId` aus einem anderen Tab), `unknown`, wenn eine Ladeantwort die Gruppe nicht mehr enthält. Ist der Haushalt gerade offen, wechselt `useLeaveRemovedGroup` zur Startseite und zeigt außer bei `self` einen Info-Toast mit dem Grund.
  - **Laden:** Die Antwort ist die Wahrheit, außer für Gruppen, deren Antwort auf eigenes Anlegen oder Umbenennen nach dem Start des Ladens kam; die bleiben, wie sie sind. Eine Gruppe, die die Antwort nicht mehr enthält, ist weg (etwa nach einem verpassten `groupRemoved`).
  - **Eigenes Anlegen:** Kommt das Neuladen nach dem eigenen `groupChanged` vor der Antwort, steht die Gruppe trotzdem nur einmal da.
  - **Listen:** Verschwindet eine Gruppe, ruft der Store `forgetGroup` im Listen-Store auf; der vergisst die Listen und über `forgetList` deren Artikel. Die Funktion ist ein Factory-Parameter, damit Tests sie ersetzen können.
  - **Offener Haushalt:** Verschwindet der Haushalt, dessen Listenansicht oder Verwalten-Seite offen ist, wechselt die App zur Startseite (`useLeaveRemovedGroup`, mit `replace`, damit „Zurück“ nicht wieder dort landet). Eine URL mit einem unbekannten Haushalt bleibt dagegen stehen und zeigt „nicht gefunden“. Einen Hinweis, warum man herausgeworfen wurde, gibt es noch nicht, siehe [#127](https://github.com/Till-und-Scholler-AI-slop/Mitbringsel/issues/127).
- **Vorladen** (`frontend/src/services/sync/preload.ts`, Phase 6, [#130](https://github.com/Till-und-Scholler-AI-slop/Mitbringsel/issues/130)): Nach jedem `ready` lädt es die Gruppen, dann für jeden Haushalt gleichzeitig die Listen (`lists.load`) und die Artikel aller aktiven Listen (`items.loadGroup`), auch von Haushalten und Listen, die der Nutzer nie geöffnet hat. So liegen sie auf dem Gerät, wenn das Netz wegfällt. Danach lädt der Artikel-Store die geladenen Listen einzeln neu, die keine Antwort abgedeckt hat (`reloadLoaded`): offene archivierte Listen und Listen eines Haushalts, dessen Anfrage scheiterte. Meldet sich in der Zwischenzeit ein anderer Nutzer an, bricht es ab. Es läuft nur bei `ready`, nicht beim Start: Mit Netz folgt `ready` sofort auf die Anmeldung, ohne Netz gibt es nichts zu laden. `main.ts` verbindet es mit den Stores.
- **Speicher auf dem Gerät** (Phase 6, ADR 0006): Gruppen-, Listen- und Artikel-Store bekommen `localData` als Factory-Parameter (`storage`).
  - **Lesen:** Das erste Laden (Status `idle`) liest den gespeicherten Stand parallel zur Anfrage. Er füllt nur, was der Store nicht hat: Was seit dem Start vom Server kam (Antwort, Ereignis), ist neuer und bleibt; was seitdem gelöscht oder verlassen wurde, kommt nicht zurück. Ist die Antwort des Servers schon eingemischt, wird der gespeicherte Stand verworfen.
  - **Status:** Der gespeicherte Stand setzt nie `ready`, damit ein alter oder leerer Stand nicht „Keine Listen“ oder „nicht gefunden“ auslöst. Scheitert die Anfrage, wartet der Store auf den gespeicherten Stand und meldet erst dann `error`; die Views zeigen dann die gespeicherten Daten statt der Fehlerbox.
  - **Server-Antwort:** Sie wird wie bisher eingemischt. Was sie nicht mehr enthält, gilt als gelöscht oder verlassen, auch wenn es nur aus dem Speicher kam.
  - **Schreiben:** Nach jedem Stand vom Server (Laden, Antwort auf eine eigene Änderung, Ereignis, Löschen, Austreten) schreibt der Store den ganzen Stand der Gruppe bzw. die Gruppenliste zurück. `persistQueue` (`frontend/src/services/storage/persistQueue.ts`) fasst Schreibvorgänge pro Schlüssel zusammen und schreibt einmal nach dem laufenden Code den neuesten Stand. Vor dem Lesen des gespeicherten Stands (und vor der ersten Antwort) schreibt der Store nichts, sonst würde ein Teilstand den gespeicherten überschreiben. `forgetGroup` entfernt die gespeicherten Listen der Gruppe, `forgetList` die gespeicherten Artikel der Liste, beide auch wenn sie in dieser Sitzung nie geladen wurden.
  - **Nutzerwechsel:** `reset()` verwirft ausstehende Schreibvorgänge. Lesen und Schreiben nennen den Nutzer, `localData` prüft den Besitzer zusätzlich.
  - **Artikel:** Für den Artikel-Store gilt dasselbe, pro Liste. Gespeichert wird nur `byList` (was der Server bestätigt hat); ausstehende Änderungen (Anlegen, Bearbeiten, Abhaken, Löschen) stehen nie im Artikelspeicher, sondern nur in der Outbox. Artikel eines ausstehenden Entfernens („Abgehakte entfernen“, einzelner Artikel) bleiben gespeichert, bis der Server sie gelöscht hat, denn bis dahin gibt es sie noch. Ein gespeicherter Artikel, den die Antwort nicht mehr enthält, ist gelöscht und kommt nicht zurück.
  - **Aufräumen:** Kein Artikel überlebt seine Liste. Neben `forgetList` sorgt dafür `localData` selbst: `removeLists` löscht die gespeicherten Artikel aller Listen des Haushalts, `writeLists` die der Listen, die im neuen Stand fehlen (archivierte Listen sind Teil des Stands und behalten ihre Artikel), jeweils in derselben Transaktion.
- **Outbox** (`frontend/src/services/sync/outbox.ts`, Phase 6, [#131](https://github.com/Till-und-Scholler-AI-slop/Mitbringsel/issues/131)): Die Änderungen an Artikeln, die noch nicht beim Server sind (`create`, `update`, `remove`, `removeChecked`), im Object Store `outbox` von `localData`. Er liegt neben dem gespeicherten Stand, nicht darin: Die Stores halten, was der Server geantwortet hat, die Outbox nur, was noch zu senden ist. Ein fortlaufender Schlüssel (`seq`) hält die Reihenfolge; `claim()` eines anderen Nutzers und Logout löschen die Outbox mit allem anderen. Vor einem Logout prüft `useLogout` deshalb `localData.readOutbox(userId)` und fragt bei ausstehenden Änderungen nach, bevor gelöscht wird.
  - **Senden:** `enqueue` speichert die Änderung und stößt das Senden an. Wer sendet, hält die Sperre `mitbringsel-outbox` (`navigator.locks`) und sendet, bis die Outbox leer ist; ein anderer Tab wartet so lange. Ein geschlossener Tab gibt die Sperre von selbst frei. Ohne `navigator.locks` sendet jeder Tab selbst, was nur die Reihenfolge zwischen Tabs ändern kann, weil doppeltes Senden harmlos ist. Ein Anlegen trägt immer die ID vom Client (im Typ erzwungen), sonst wäre es nicht wiederholbar.
  - **Halten:** `enqueueHeld` holt zunächst eine eigene Web-Lock (`mitbringsel-outbox-hold-<UUIDv7>`) und legt zusammengehörige Änderungen in Reihenfolge mit diesem `hold`-Namen ab. Trifft die Outbox beim Senden auf einen gehaltenen Eintrag, wartet sie (nach der 30-Tage-Prüfung) auf dessen Sperre (Head-of-Line); spätere Änderungen warten dahinter. `release()` gibt die Sperre frei, `cancel()` entfernt die Einträge zuerst ungesendet und gibt sie dann frei, und `stop()` gibt alle gehaltenen Sperren dieser Outbox frei (wie ein geschlossener Tab). Ohne `navigator.locks` sorgt eine Warteschlange pro Sperrname im Tab dafür, dass der eigene Sender den Hold beachtet; ein anderer Tab kann den Eintrag dann allerdings schon vor „Rückgängig“ senden.
  - **Fehler:** Netzfehler, 5xx, 408 und 429 wiederholt sie: Wartezeit vor Versuch *n* (ab 0) = `min(60 s, 1 s · 2^n) · (1 − 0,5 · Zufall)`, bei 429 so lange, wie `Retry-After` sagt. Die Änderung bleibt dabei vorn, die übrigen warten hinter ihr. Bei 401 hält sie an, behält alles und sendet erst nach `trigger()` wieder (nicht bei einer neuen Änderung). Jedes andere 4xx verwirft die Änderung (`onRejected`). `remove` mit `ITEM_NOT_FOUND` zählt als gesendet. Eine Änderung, die älter als 30 Tage ist, verwirft sie ungesendet mit `OUTBOX_EXPIRED`.
  - **Rückmeldung:** `onSent` mit der Antwort des Servers und `onRejected` mit dem Fehler kommen nur im Tab, der gesendet hat, und nur, solange derselbe Nutzer angemeldet ist. `subscribe` meldet jede Änderung der Outbox, auch aus anderen Tabs (`BroadcastChannel`). `trigger()` sendet sofort und beendet eine laufende Wartezeit.
  - **Ohne IndexedDB** hält der Tab die Änderungen im Speicher und sendet sie trotzdem; ein Neuladen verliert sie dann.
  - Der Artikel-Store besitzt sie ([#132](https://github.com/Till-und-Scholler-AI-slop/Mitbringsel/issues/132), [#133](https://github.com/Till-und-Scholler-AI-slop/Mitbringsel/issues/133)); `trigger()` bei `ready` folgt mit [#134](https://github.com/Till-und-Scholler-AI-slop/Mitbringsel/issues/134).
- **Sync-Chip** (`BaseSyncIndicator`, über `SyncStatus` in den Köpfen von Start, Liste und Verwalten und in der Desktop-Seitenleiste): Der Sync-Store leitet `indicator` ab. `connected` ist „Synchron“, `offline` ist „Offline“, `connecting` gilt 2 Sekunden lang als „Synchron“ und danach als „Offline“, damit der Chip beim Laden und bei kurzem Wiederverbinden nicht flackert. Die Frist läuft im Store, nicht im Chip, damit ein Seitenwechsel sie nicht neu startet. „Ausstehend“ kommt mit der Outbox in Phase 6.
- **„Gerade geändert“** (`frontend/src/stores/recentChanges.ts`): Ein `itemChanged` mit fremder `actorId` hebt den Artikel 5 Sekunden lang hervor, mit dem Namen des Mitglieds („Ben · gerade geändert“). Eine spätere Änderung startet die Zeit neu, eine eigene beendet die Hervorhebung, Löschen auch. Nur Ereignisse zählen, weil nur sie sagen, wer geändert hat; ein Neuladen nach `ready` hebt nichts hervor. Abgehakte Artikel werden nicht hervorgehoben (Design). Der Store hört selbst auf die Ereignisse, der Artikel-Store bleibt unberührt.
- **PWA und Service Worker** (`frontend/pwa.config.ts`, `frontend/vite.config.ts`, Phase 6, [#136](https://github.com/Till-und-Scholler-AI-slop/Mitbringsel/issues/136)): `vite-plugin-pwa` im Modus `generateSW` erzeugt `sw.js`, `registerSW.js` und `manifest.webmanifest`.
  - **Caching:** Der Service Worker speichert nur die gebaute App-Shell und statische Assets vorab (`globPatterns`), nie `/api` (`runtimeCaching: []`). API-Daten liegen ausschließlich in IndexedDB.
  - **Navigation:** SPA-Deep-Links fallen offline auf `/index.html` zurück; `/api`-Pfade (z.B. Google-OAuth-Callbacks, WebSocket) sind per `navigateFallbackDenylist` (`/^\/api(?:\/|\?|$)/`) ausgenommen und gehen immer zum Server.
  - **Updates:** `registerType: 'autoUpdate'` übernimmt neue Versionen beim nächsten Laden. Ausstehende Änderungen in der Outbox und der lokale Speicher in IndexedDB bleiben dabei erhalten.
  - **Entwicklung und Auslieferung:** In `npm run dev` bleibt der Service Worker aus (`devOptions.enabled: false`), damit Vite-Proxy und WebSocket unberührt bleiben. In Produktion liefert `frontend/nginx.conf` `manifest.webmanifest` (`application/manifest+json`), `sw.js`, `registerSW.js` und `workbox-*.js` mit `Cache-Control: no-cache` und `=404` (ohne Fallback auf `index.html`) aus; gehashte Dateien unter `/assets/` bleiben `immutable`.
- **Bekannte Grenze:** Ab dem 11. offenen Tab bekommt eine Verbindung `429` und bleibt offline, siehe [#110](https://github.com/Till-und-Scholler-AI-slop/Mitbringsel/issues/110).

## Abgrenzung erstes Release

Artikel sind voll offline-fähig. Gruppen, Einladungen und Listen werden zunächst online über REST verwaltet. Ihre Änderungen werden aber per WebSocket als Ereignis an alle Mitglieder verteilt (`listChanged`, `groupChanged` …), damit neue Listen sofort bei allen erscheinen.
